# Step 6: a smoke test and CI

Goal: one command that builds the program, runs it headless, and checks that every earlier step still produces
its expected output, ending with a deterministic power-off; and a GitHub Actions workflow that runs it.

Files: [`tests/smoke.sh`](../../tests/smoke.sh), [`src/psci.c`](../../src/psci.c),
[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml).

## Ending deterministically: PSCI SYSTEM_OFF

A test needs the program to finish by itself. PSCI is the Arm standard interface for power control: the caller puts a
function ID in `w0` and executes `smc` (to EL3) or `hvc` (to EL2). Function IDs used here:

| ID | Function |
|---|---|
| `0x84000000` | `PSCI_VERSION` |
| `0x84000008` | `SYSTEM_OFF` |

My first attempt used `hvc`, as `virt -M virtualization=on` would normally provide PSCI through HVC to a kernel. It
did not work: with `secure=on` the program starts at EL3, so *it* is the firmware, and QEMU does not provide
PSCI there. An `hvc` goes to EL2 (which has no handler), and an `smc` reaches EL3's own vector table as an SMC exception
(EC `0x17`). So the program implements the call itself:

- EL1 (`psci_system_off`) puts the function ID in `x0` and executes `smc #0`.
- The call is taken to EL3: vector entry 8 (lower EL, AArch64, Sync), `ESR_EL3.EC` = `0x17`. `exception_handler` sends
  it to `psci_el3_handle`.
- `PSCI_VERSION` returns `0x00010000` in `x0` (the saved copy in the trap frame, restored on return). `ELR_EL3`
  for an `smc` points to the next instruction, so `eret` continues the caller.
- `SYSTEM_OFF` has to stop the machine. QEMU `virt` with `secure=on` has a Secure-only PL061 GPIO at `0x090b0000`
  whose output pin 0 is wired to "power down" (found by experiment: driving each pin high in turn, pin 0 ends the run
  with status 0). Set `GPIODIR` bit 0, then write 1 to the data register for pin 0.

## `tests/smoke.sh`

- builds with `make`;
- runs QEMU with `-nographic -smp 4` and a `timeout`, input from `/dev/null`;
- requires QEMU's exit status to be 0, which only happens when the program powers off (status 124 would be the timeout);
- greps the output for the lines each step must print, one `PASS`/`FAIL` line per check, and a non-zero exit if any failed;
- checks that the banner appears once, which shows that the three extra cores were parked;
- `CPU=max tests/smoke.sh` repeats the run with another `-cpu` value.

Example (all 33 checks pass for both `-cpu cortex-a53` and `-cpu max`):

```
PASS  exit: QEMU exited with status 0 (PSCI SYSTEM_OFF)
PASS  1-boot: CurrentEL = 0xc (EL3)
...
smoke: all checks passed (-cpu cortex-a53)
```

The checks are on exact register values (`ESR_EL1=0x96000021`, `FAR_EL1=0x40000001`), which are properties of the
architecture, not of timing. The only run-to-run differences are the timer counts, which are not compared.

## The workflow

`ubuntu-latest`; apt installs `gcc-aarch64-linux-gnu` and `qemu-system-arm` (the Ubuntu package that holds
`qemu-system-aarch64`); then `tests/smoke.sh` for two `-cpu` values, and the UART output is kept as an artifact. It
runs on pushes to `main` and on pull requests. The repo has no remote yet, so it has not run on GitHub; the same
script passes locally.

## RV32 comparison

| RV32 | AArch64 here |
|---|---|
| an `ecall` into M-mode firmware (SBI) | an `smc` into EL3 firmware (PSCI); here the EL3 firmware is this program |
| `tohost` write or an SBI call ends a run | PSCI `SYSTEM_OFF` ends the run |
| riscv-tests print and exit through `tohost` | the smoke test greps the UART and checks QEMU's exit status |

## Check yourself

1. Why did `hvc` not end the run?
2. Which `ESR_EL3.EC` identifies an SMC, and which vector entry takes it from EL1?
3. Why does the smoke test check QEMU's exit status as well as the output?
4. Why does the test not compare the timer counts?
5. Why does the workflow install `qemu-system-arm` to get `qemu-system-aarch64`?

<details>
<summary>Answers</summary>

1. The program boots at EL3 and is its own firmware; QEMU only provides PSCI when it is not. `hvc` went to EL2,
   where no handler is installed.
2. EC `0x17`. From EL1 (a lower level, AArch64) it uses entry 8, offset `0x400`.
3. Output alone cannot tell "finished and powered off" from "hung after the last line". Status 0 proves the power-off happened.
4. They depend on host scheduling (each run differs by a few percent). The tick count and the registers are exact.
5. Ubuntu builds the Arm 32-bit and 64-bit system emulators into one package.
</details>

## Break it

In `psci_el3_handle` change `GPIODATA_PIN0 = 1;` to `= 0;`. Predict: the pin never rises, QEMU does not exit, the
`wfe` loop spins, and `tests/smoke.sh` fails on the exit-status check (124), although every output line is still
present. Run `tests/smoke.sh` (it takes the full timeout; use `TIMEOUT=10`) and read the first line of its output.
